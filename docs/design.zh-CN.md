# MOLite Core 设计草案

状态：保留设计目标；2026-10-24 已实现的运行链路、兼容边界和实际 API 见 README、docs/api.zh-CN.md 与实施记录。以下建议不自动等于实现承诺。

## 1. 已确定的产品边界

MOLite Core 基于 MOMO Core，集中提供具有 MO State v2 与 DMW 的角色对话运行时，目标是轻量、快速、配置简单。以下以用户已确认的要求为准，不将实现建议冒充需求。

| 项目 | 已确定边界 |
| --- | --- |
| 核心 | MO State v2、DMW，保留自治维护与恢复能力 |
| 角色格式 | 只使用原生 MOC，不兼容外部角色卡 |
| 空间 | 没有个人空间、角色级记忆或共享记忆体系 |
| 场景与会话 | 已解释消息序列与当前叙事状态的职责差别；最终命名、映射未固定 |
| 记忆注入 | 只向场景注入，范围由用户明确选择或切换 |
| 分类 | 文件夹、标签，仅用于组织资源 |
| 自动提炼 | 默认每 12 个未处理的完整问答一批，允许自定义轮数及提前提炼 |
| 模型设置 | 服务商下先配置文本、视觉模型，再配置可复用的模型参数组 |
| 模型用途 | 对话、记忆、视觉回退分别选择模型参数组 |
| 模型参数组 | 包含所选模型、请求方式与请求参数，不是三个用途装在同一个组里 |
| 模型接口 | 沿用前文的三种：OpenAI 兼容 Chat Completions、OpenAI Responses、Anthropic Messages |
| 多模态 | 支持图片输入；原生看图和视觉回退按对话模型能力处理 |
| 数据文件 | 存储 TXT、PNG、PDF 等数据文件，默认可随 MOC 携带，也可选择排除 |
| 消息修改 | 编辑、重生、删除使相应来源失效，按强索引重新提炼并告知用户 |
| 对外入口 | Rust API、HTTP、标准 C ABI 三种都保留 |
| 排除能力 | LSB、图片载体、外部角色卡兼容、NSG、Turso 向量存储 |

MOC 携带业务数据、模型接口集合和三种接入方式已确认。提炼默认 12 轮，用户可调整间隔或提前执行。数据库布局、限额、版本化字段等属于工程方案。

## 2. 场景与会话的含义

MOMO 原来的“会话”负责消息序列，“场景”表示其中当前的时间、地点、参与者、焦点与开放线程。同一会话可以从客厅转到车站，因此这两个词在原系统中有不同职责。

用户此前将这两个词近似使用是术语尚未区分，不是要求产品强制合并或统一叫“场景”。最终命名及资源映射尚未固定，不把此前的解释误记为已确认需求。

保留消息序列、当前叙事状态、记忆注入范围的职责区分即可；是否分别使用 `conversation_id`、`scene_id` 或采用内部映射，在接口契约中明确。本文后续“场景”用于讨论用户指定的记忆注入情境，不预先决定界面名称或强制一对一关系。叙事地点改变也不必自动创建新会话。

角色是内容资产及事实参与者。角色 ID 可以出现在消息和来源中，但不拥有长期记忆池；使用同一个角色打开另一个场景不会自动继承记忆。文件夹、标签的移动、重命名与删除不改变记忆范围、模型设置或来源索引。

不增加独立剧情分支的隐式记忆继承。复制或新建场景也不自动扩大注入范围。

## 3. 场景记忆及注入范围

记忆只能通过明确的场景注入范围使用。不提供角色级记忆、全局共享池、个人 Space 或按角色自动检索全部历史的路径。

每条记忆保留来源场景、原始证据与必要适用性信息，不能仅因角色相同、分类相同或内容相关而进入另一个场景。用户若希望延续记忆，应主动调整“注入场景范围”；Core 按该范围检索和注入，不将这项显式选择转成自动共享策略。

注入范围的具体 wire 结构尚待实现细化，必须能表达用户选择的场景范围及版本。不因内部实现便利新增记忆 Space、角色池或共享授权资源。

范围仅控制读取与注入，不复制原始记忆、不改写来源、不把外部场景的经历自动登记为当前角色亲历。新证据和提炼结果写回其来源场景，不因读取其他范围获得任意改写其他场景事实的权限。

用户切换范围后，新请求捕获新范围及 revision；已完成响应的历史上下文保持不变。旧缓存须重新检查资格，不得继续注入已移出范围的记录。用户明确选择读取记录也不免除事实主体、认知边界与来源版本检查。

## 4. MO State v2 与 DMW-only profile

MOMO 的 MO State v2 规范依赖 DMW、NSG 和原生响应运行时。MOLite 需要明确自己的 DMW-only profile，列出继承行为及裁剪项，不能删除 NSG 后宣称完整实现原规范。

保留运行主体的职责：

- 事件入口、稳定排序、单写提交与场景内部状态管理。
- DMW 提案校验、增量提炼、生命周期与引用保护。
- 同一输入版本的一致快照、五维投影、上下文预算。
- 持久队列、幂等、取消、有限重试、恢复及降级诊断。
- 来源、参与者、认知资格及用户选择的场景注入范围检查。

快照属于可重建派生视图，不能反向变成新的事实证据。模型只能提出结构化变更，由运行时校验提交。

| 五维状态 | MOLite 输入边界 |
| --- | --- |
| `scene_constraint` | 当前场景内部叙事状态及原生角色中的明确限制 |
| `physiological_state` | DMW 中有证据的伤病、疲劳等状态 |
| `epistemic_state` | 来源与参与者支持的知情、亲历、秘密边界 |
| `relational_stance` | 经场景注入范围允许且有依据的关系与承诺 |
| `emotional_tone` | 经验证的状态信号，不将瞬时语气直接固化 |

重写依赖 NSG 的内置契约。例如 MOMO 默认伤势规则同时依赖 DMW `wounded` 与 NSG `injury`，MOLite 应根据明确伤势证据给出保守约束，不保留永远无法命中的条件。

DMW 保留动态事实、经历、偏好、关系、承诺、事件、当前叙事状态及其自身有界 `relations` 扩展。自动维护不把一句新世界规律直接确立为作者设定，也不重建 NSG Canon/Draft 治理体系。

不保留 NSG revision、embedding profile 或空 NSG 协议占位。建议不引入其他向量数据库替代 Turso，沿用 DMW 确定性词元、别名、标签、正文索引和有界 1-Hop 检索。

## 5. 可配置提炼周期、提前提炼与前台投影

自动提炼默认每 **12 个未处理的完整问答** 一批，用户可设置间隔；初始实现沿用 MOMO 的 1–200 轮范围。一轮通常是一条用户消息和一条成功提交的助手回复，不是 12 条单独消息。消息、来源、参数组配置与范围等必要上下文应在入队时捕获；批次不混淆不同来源场景。

用户可以提前提炼未满阈值的待办。成功后，已消费轮次不再计入下一周期：例如第 5 轮提前成功，则无并发新消息时再等 12 轮，在总第 17 轮到期。处理期间新增消息继续作为下一周期待办，不被清空。失败不重置计数，重启恢复同一证据批次。已有批次先恢复；积压超过单批上限时由后续 worker 按批排空。

批次读取新证据和必要的已有记忆，生成增量 Patch，而不是每 12 轮重读全部历史或强制重写全部文档。失败保留原批次，重试不重复确认成功轮次。

前台 MO State 每次生成前仍从已提交 DMW、当前叙事状态与合格输入投影状态，不等待满 12 轮，也不因此每轮额外调用一次记忆模型。近期消息继续进入受预算约束的对话上下文。

默认值保持 12，用户修改间隔作用于后续新批次，不重写已捕获批次。提前提炼是对自动周期的提前执行，不是另一套独立计数，也不取消自动维护。

消息源修正触发的重新提炼属于一致性修复，不等待积累 12 个新问答。低层权重维护与生命周期也不等于模型提炼。生命周期建议继续采用已完成交互轮次，闲置时间不推进剧情或凭空产生事实。

## 6. 强来源索引与重新提炼

来源不能只保存一段可读说明。需要可反向查找的稳定关联，至少区分：

```text
场景 ID + 消息 ID + 消息 revision / 有效版本
数据文件 ID + 内容哈希 / revision（存在文件证据时）
    -> 证据记录
    -> 派生记忆及其 revision
    -> 依赖的状态快照 / 索引
```

消息编辑、重新生成或删除后：

1. 标记原消息证据版本失效；重新生成时旧候选不再作为当前有效消息。
2. 通过反向索引找到受影响的记忆、提案、批次及状态缓存。
3. 立即使失效证据支持的旧结果退出注入或进入待校验状态，不能边显示“重提炼中”边继续把旧事实当作有效事实。
4. 根据当前有效消息、其余证据和明确依赖重新提炼受影响范围。多来源事实应重新核查剩余依据，不无差别删除全部记忆。
5. 原子提交新记忆、来源和索引版本，刷新场景状态，告知用户处理结果。

修复不是自动重生成所有后续聊天消息。已有消息仍是历史内容；其派生记忆若依赖被改写的证据，需要沿依赖关系重算，不能只更新一个来源标签就声称修复完成。

修复不增加新的完整问答计数，不因重新执行同一批次重复推进生命周期；未处理队列使用当前有效消息版本，被删除的版本不得在稍后的 12 轮批次中重新成为证据。

Core 提供已受理、重新提炼中、完成、失败/待重试等事件，以及受影响范围和可读原因，宿主负责呈现通知。正常修复自动执行，不再要求用户逐条批准。失败时明确报告，不重新启用已失效证据。

删除整个场景同样触发相关证据与派生记录处理，不能将其曾产生的记忆默认永久留在另一种角色池里。资料或导入证据拥有独立来源类型，不伪造聊天消息 ID。

## 7. 服务商、模型与模型参数组

配置顺序固定：

```text
服务商（地址、协议能力、凭据）
    -> 文本 / 视觉模型（实际模型 ID、上下文、输入输出能力）
    -> 模型参数组（模型引用、请求方式、请求参数）
    -> 对话 / 记忆 / 视觉回退分别选择组
```

**模型参数组是一份可复用的模型请求配置。** 同一模型可建立多个组，例如“流式对话”“低采样提炼”；不是一个组固定装入三个用途，也不是角色分类组、记忆范围或场景配置组。

三个用途是参数组的使用位置：对话选择可用生成组，记忆选择提炼用组，视觉回退选择具备图片输入能力的组。组被复用时，其显式参数按组定义执行；用途不得悄悄改写它。未指定参数才采用 Core 的用途推荐默认值，解析结果及限制可查询。

示意结构，尚不是最终 wire contract：

```json
{
  "id": "parameter-group-id",
  "name": "日常流式对话",
  "revision": 1,
  "model_ref": "configured-model",
  "request": {
    "protocol": "openai_chat_completions",
    "stream": true,
    "parameters": {
      "temperature": 0.8,
      "max_output_tokens": 2048
    }
  }
}
```

请求方式支持前文已列明的三种接口：OpenAI 兼容 Chat Completions、OpenAI Responses、Anthropic Messages。参数组选择其服务商实际可用的方式，并配置流式偏好及协议适用字段；不能把这项能力删成“组里只允许采样参数”。

服务商提供连接及可用接口，模型声明能力，参数组细化实际请求。配置不一致时明确报错，不自动猜协议、失败后切协议或静默换模型。组中通用参数及扩展字段不能越权重写凭据、任意目标地址、消息证据或内部控制命令。流式偏好还应验证用途执行契约，例如后台提炼是否能可靠消费该响应形式。

省略参数继承用途默认，显式 0 保留；恢复默认删除自定义覆盖，不复制默认 JSON，不更换模型或请求方式。通过 revision 原子发布，已接受请求和维护任务继续使用捕获组版本、连接引用及有效参数。

请求记录三个用途实际选用的组，不需要再规定“参数组属于角色还是会话”才能定义组本身。宿主可以保存常用选择，Core 以本次提交或已捕获的引用为准；具体默认选择的持久化字段属于接口细化。

凭据只在本地连接管理中解析，不能进入日志或 MOC。模型参数组不属于原生角色定义，不强制写入角色卡。

## 8. 图片请求与数据文件

数据文件是正常消息文本之外的独立内容资源，可包含 TXT、PNG、PDF 等，不限于图片或视觉描述。存储文件、读取文件和把文件送给模型是不同步骤，不能把“文件已保存”当成“模型已读取”。

每个文件需要稳定 ID、原始名称、类型、字节长度、内容哈希及存储位置，消息或场景通过关联引用它。模型实际使用的原文件、提取文本或视觉描述应记录来源，后续文件替换同样触发证据版本处理。

图片请求按能力处理：

- 对话模型支持视觉：文字与原图以有序内容块组成一次对话请求，使用对话模型参数组。
- 对话模型仅支持文本：图片交给视觉回退组生成描述，再把描述与用户文本交给对话组。
- 纯文本输入不调用视觉回退；需要回退却缺少有效组时明确报错，不忽略图片继续生成。

TXT 可通过受限解码生成文本；PNG 按图片输入处理；PDF 的内容提取或协议原生输入适配需按实际支持实现。三个接口对文件输入形式可能不同，适配器需明确支持范围。不能因为会存储 PDF 就宣称所有模型接口已经支持 PDF 请求。

视觉描述和文档提取结果是带来源的派生内容，不自动成为亲历、作者设定或长期事实。图片文字、文档正文或模型描述不能改写运行配置。实际输入预算涵盖文本、原生图片/文件成本、提取内容和输出预留；限额在输入契约中集中定义。

数据文件是可持久保存的业务数据，不再采用“原图一律处理后删除、只留下描述”的建议。用户删除文件或选择临时处理时按明确操作执行；清理不能静默破坏仍在使用的证据引用。

成功回退描述及提取结果按输入哈希和处理配置版本持久记录，重放可复用已保存结果。上游已处理但结果尚未落盘的故障窗口仍不能保证只计费一次。

不支持 LSB 编解码、图片角色卡元数据提取或图片承载 MOC；普通 PNG 附件与图片载体是不同用途。

## 9. MOC 沿用原生格式与携带能力

保留原版 MOC 的原生容器及业务数据携带设计：可按原有选择机制携带角色、场景/会话、DMW 等受支持内容，不新增“首版只能单角色包”限制。原生角色内容继续使用 `character.toml`、`character.md` 以及可选的 `user.md`、`opening.md`；外部 JSON、PNG、CHARX 角色卡兼容不加入。

数据文件一般随相关业务数据进入 MOC，用户也可明确选择不携带。TXT、PNG、PDF 等原始文件可以作为数据文件负载存储，不以全部转成纯文本代替原文件。排除文件时必须报告所缺文件或引用状态，导入端不能假称已恢复原始附件。

MOC 保留已有版本、完整性、路径安全、模块声明和选择规则；已有加密封装沿用原生契约，不因 MOLite 轻量目标擅自删除。已排除的 NSG 等能力不因出现在容器里重新成为运行能力，不支持的内容须在预检中说明。

现有 MOC v3 线格式包含 `space_modules` 与 `.../spaces/<uuid>/...`。这些字段在解析、来源保留和重新打包时处理，不建立 MOLite 运行时个人空间。会话来源可映射为统一场景 ID；不能将多个来源因为角色相同就合成一份记忆，更不能让文件夹代替原始身份。映射细节需在原生 MOC 适配文档中固定。

原生格式可用宿主扩展携带文件等附加数据。具体模块归属应核对原版已有约定，已有者沿用，没有者明确记录扩展 schema；不得悄悄改 manifest 含义后仍宣称完全兼容原版。保留强来源索引、记录 revision、文件引用及关联哈希，导入不能伪造本地可验证证据。

导出应固定一致版本；导入先完整预检，再提交业务变更。ID 冲突、排除数据文件或不支持模块须明确报告，不能静默覆盖或丢失。凭据、机器本地连接秘密和无关运行缓存不进入 MOC。

## 10. 三种接入入口

Rust API、HTTP、标准 C ABI 均为保留的正式入口，连接同一套 Core 操作与运行时，不因采用嵌入式 API 而要求额外启动 HTTP 服务。

| 入口 | 责任 |
| --- | --- |
| Rust API | 类型化业务操作与事件流 |
| HTTP | 独立服务、请求与事件/SSE 传输 |
| C ABI | C 头文件、平台动态库、不透明句柄和明确的内存所有权 |

三种入口覆盖角色与 MOC、会话及叙事状态、注入范围、文件分类与存储、服务商与模型、模型参数组、响应、记忆重新提炼及诊断。错误码语义、幂等、取消、快照与通知行为一致，不各自实现一套记忆引擎。

C ABI 已实现，结构、生命周期和事件拉取见 [实际接口](c-abi.zh-CN.md)。Windows x64 已以真实 C 调用验证；早期指针方案保留在历史草案中。

## 11. 持久化与复用建议

建议一个 SQLite 业务库保存场景消息、DMW 逻辑文档、来源与反向索引、版本、模型配置、任务和必要审计。数据文件可使用独立内容存储，数据库保存关联及哈希，避免强制把大 PDF、PNG 全部装入数据库。

```text
data/
  molite.sqlite3
  files/<content-hash>/...
```

这是工程建议，尚未确认具体布局。文件内容先写入、校验并持久化后再发布数据库引用，失败或崩溃产生的暂存/孤立文件需可恢复清理。不能把文件系统和 SQLite 的组合伪装成同一原子事务；导出与清理也须保护仍被使用的文件。

DMW 仍保留逻辑文档及原生文本语义，MOC 导出时生成需要的文档。数据库方案改变 MOMO 文件 journal 的实现布局，需明确记录，不能直接搬用文件写入器后声称已完成存储适配。

模型网络 I/O 不持有数据库写事务。响应完成时，助手消息、幂等结果、提炼入队与生命周期事件应原子发布；失效来源和状态缓存不能跨事务间隙被当成有效事实使用。

Rust 内部先采用清晰模块：领域、场景、DMW、MO State、MOC、数据文件、分类、模型连接、参数组、持久化、编排，以及 HTTP/C ABI 边界。裁剪不需要的依赖，不依赖完整 MOMO 再用开关隐藏功能。不引入未经请求的通用 Agent、NSG、向量引擎或账号系统。

## 12. 验证与剩余工程细化

实现验收至少包括：

- 相同角色的不同场景不会自动获得彼此记忆；只有明确调整注入范围才改变读取资格。
- 文件夹标签不改变场景记忆范围；模型参数组确实决定请求方式及实际参数。
- 12 轮增量提炼、失败恢复、前台状态投影及上下文裁剪不会遗漏证据。
- 编辑、重生、删除和文件替换能定位依赖、撤下旧事实、重新提炼并发出通知。
- 原生看图不多调用视觉回退，回退结果和文件提取内容有明确来源。
- MOC 中角色、场景、记忆、数据文件及索引可往返；选择不携带文件时准确报告缺失。
- 三种模型接口及三种接入入口使用一致行为；C ABI 由真实纯 C 宿主验证。
- 同请求重放不重复提交消息或提炼任务，流式输出以持久提交后的完成事件为准。
- 记录发布体积、冷启动、空闲及峰值内存、本地编排 p50/p95；模型网络时间单列。

剩余主要是工程契约：场景/会话命名及映射、注入范围的具体字段、原生 MOC 来源映射与数据文件模块、请求参数映射和默认值、文件/上下文限额、存储恢复协议、ABI/HTTP schema 及平台构建矩阵。不再将已确认产品要求重新列为用户选择题。
